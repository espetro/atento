| Pairing status | static | "paired? / last capture?" — needs a pairing-status read [gap: M4b or later]; until then show "status unavailable — check the extension" honestly, never a guessed state |

The UI NEVER calls POST /api/pair — redemption is the client's job. Note the loopback trust tradeoff the server documents: on loopback the code endpoint is unauthenticated by design (bounded: 39-bit codes, single-use, 5-min TTL, rate-limited) |

## Behavior

- Strictly read-mostly. The ONLY mutations in v1: GET /api/pair/code
  (issues a code — technically a POST-free read-shaped call, but it
  mutates server state by minting a code; label the button accordingly
  and treat it as the single write-ish action on the page) and copy
  buttons. Everything else is display + deep links. This is deliberate:
  config.toml/harness.toml are the source of truth and hand-editing
  beats a half-editor that drifts from the parser (smol-toml,
  additive sections).
- The pairing contract is the REAL M5 one — no speculative
  POST /api/pairing. GET /api/pair/code returns `{code, expiresAt}`;
  POST /api/pair {code} → `{captureToken, serverToken}` is redeemed by
  the extension only (either token may be null when the corresponding
  env var is unset — the explainer should say so). Both endpoints ship
  on feat/m5; until M5 merges the button renders disabled with
  "pairing endpoint not available in this build".
- [gap] Most config sections need a config-read endpoint that does not
  exist (M4b). Interim: sections that can't read config show the file
  path + `linkinbox browsers --json` / `linkinbox config` style
  commands to run in a terminal, clearly labeled "CLI". Do NOT
  fabricate values.
- Browser adapters section is the highest-value gap to close:
  `linkinbox browsers` already computes kinds/caps/roles/health —
  exposing it as GET /api/browsers is a small server change (M4b) and
  makes this section real.
- Schedule section never shows a next-run time it can't know — the
  harness owns recurrence (harness.toml `schedule`/`on_ingest`). If a
  harness later reports schedule metadata it can slot into the same
  row; until then "unknown — set it in harness.toml" is honest.
- Server card derives auth state from the client's own experience:
  if the UI loaded without a token prompt on a non-loopback bind it
  knows auth passed; it must not claim "no token required" for a
  non-loopback bind it wasn't told about — show "loopback" only when
  the server reports the bind (needs [gap] server-info in /api or
  openapi, M4b).
- Accessibility: tables use real `<table>` semantics; copy buttons
  announce "copied" via aria-live; the pairing code is in a
  `role="status"` region so its one-time nature is announced; expiry
  is text, not just a countdown color.
- Mobile: cards stack full-width; the adapters table becomes a
  definition-list per adapter (id/kind/caps/roles/health) under 760px.
